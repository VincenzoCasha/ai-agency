1. Executive Summary of the V1

CRUDO's V1 website is not a marketing brochure. It is a single-owner-operator's commercial multiplier — a digital system that turns Instagram followers, local search, and curiosity into in-store visits and pickup pre-orders, with one explicit business outcome:

Generate enough sustained revenue to fund the first hire (a second person on the floor) within 12 months — so the owner can step out of the bar long enough to grow the business toward a second location in 2–3 years.

Every scope decision in this plan is filtered against that North Star.

The V1 turns traffic into:

  1. Walk-ins to the physical bar.
  2. Cheese & non-alcohol pickup pre-orders (paid in store — no online payment in V1).
  3. Wine discovery (browsable catalog, but reservation/inquiry handled by WhatsApp — no online alcohol sale).
  4. Event / tasting attendees.
  5. A growing email list for seasonal campaigns.

The site adopts a dark, editorial, gastronomic visual language — dark olive backgrounds, cream serif headlines, warm product photography — coherent with the Piscolabis reference family but distinguished by CRUDO's own palette accent (muted terracotta) and typography (Cormorant Garamond + Inter).

The stack is intentionally lean: React 19 + Vite frontend, Node.js + Express backend, and MariaDB, packaged as a CommonJS monolith where server.js serves both the API and the built dist/ assets in production. Local development runs with npm scripts and production is deployed on a Contabo server managed with Plesk. Architecture is modular-monolith — small enough to ship in 6–8 weeks, structured enough to evolve into proper ecommerce in V2 once the first hire is in place.

Pickup orders in V1: YES — but as a "reserve & pay in store" inquiry flow, restricted to non-alcohol products. Wine is visible in the catalog (drives discovery) but routes to WhatsApp instead of the cart. This is the single highest-leverage scope decision: it delivers commercial value from day one without dragging legal, payment, and alcohol-online-sale compliance into a first launch.

Language: Spanish primary; English readers handled by Google Translate auto-translation (semantic markup + a discreet language hint). Full i18n is deferred to V2.

Operational rule: the admin panel and notification flow must let the owner manage everything from a phone in ≤ 5 minutes a day between serving customers.

9. Technical Architecture

Pattern: CommonJS modular monolith: Express API + React 19/Vite frontend + MariaDB. In development, Vite and Express run with npm scripts; in production, server.js serves dist/ and the API from one Plesk Node.js app.

Justification for Node.js/Express: CRUDO's V1 benefits from one simple JavaScript stack across frontend and backend. Express is familiar, easy to deploy on Plesk, and enough for the V1 API surface. MariaDB fits Plesk/Contabo hosting naturally, avoids extra managed services, and keeps operations visible in one panel.

Why a SPA + API (not server-rendered): - The frontend is content-light and interaction-rich (cart-like Mi Tabla, filters). - Decoupling keeps the door open for a future Next.js/SSR migration if SEO needs deepen. - For V1 SEO needs, we use prerendering for the catalog and product pages (via vite-plugin-ssg or a small prerender step at build time) so Google indexes them properly. This is the V1 SEO compromise — no Next.js complexity, but no client-only SEO pain either.

Hosting (recommended): - Contabo VPS/server managed with Plesk for domain, SSL, Node.js app hosting, MariaDB, file storage, and backups. - Local development uses npm run dev; production uses vite build and node server.js through Plesk. - Product images live on the server filesystem managed by Plesk for V1. External object storage/CDN is deferred until real traffic or image volume justifies it. - Backups: Plesk scheduled backups for database/files plus Contabo backup/snapshot option where available.

Why not serverless / Vercel / managed DB for V1? A Contabo + Plesk setup is easier for the owner/operator context, keeps domain/SSL/backups in one visible panel, and avoids splitting a small V1 across too many providers. V2 can split if needed.

Notes: prices stored as *_cents (integer) to avoid float pitfalls. slug indexed and unique. is_active on every public-facing entity for soft-publishing. All tables have created_at/updated_at.

Designed-for-but-not-built (V2 readiness): - A future location table is anticipated. To avoid premature complexity, V1 keeps no location_id foreign keys, but every entity is migration-friendly: a single ALTER + nullable location_id plus a default seed row will retro-fit a multi-location model when a second location is opened in 2–3 years. - A language field on Product is not added in V1 — Spanish copy + Google Translate covers the use case. V2 i18n will add product_translation table when full English/Catalan is justified.

13. Recommended API Endpoints

All under /api/v1. Public endpoints are cacheable (CDN-edge, 5 min). Admin endpoints require Authorization: Bearer <JWT>.

Public

GET /products/{slug} Product detail with images & related
GET /categories All categories grouped by type
GET /campaigns/active Currently active campaigns
GET /campaigns/{slug} Single campaign with featured products
GET /events Upcoming events
GET /events/{slug} Event detail
POST /events/{slug}/reservations Reserve a seat (rate-limited, captcha)
POST /inquiries Generic contact / wholesale form
POST /pickup-orders Submit a "Mi tabla" pickup inquiry. Server rejects with HTTP 422 if any line item references a product with is_alcohol=true — alcohol must use the WhatsApp path
POST /newsletter/subscribe Subscribe to newsletter (double opt-in via Brevo)
GET /site/config Hours, address, holiday closures, hero settings

Admin (JWT-protected)

Method Path Purpose
POST /admin/auth/login Email + password → JWT
POST /admin/auth/refresh Refresh JWT
GET/POST/PUT/DELETE /admin/products CRUD products
POST /admin/products/{id}/images Upload image (multipart → Plesk/server filesystem for V1; external object storage deferred)
GET/POST/PUT/DELETE /admin/events CRUD events
GET/POST/PUT/DELETE /admin/campaigns CRUD campaigns
GET/PATCH /admin/inquiries List & update inquiry status
GET/PATCH /admin/pickup-orders List & update order status
GET/PATCH /admin/event-reservations List & update
GET/PUT /admin/site/config Edit hours, hero, etc.

Cross-cutting

  • Pagination: page, size (default 20).
  • Errors: RFC 7807 application/problem+json.
  • Rate limiting on POST endpoints: 10 req/min/IP via Bucket4j.
  • CORS: only the public domain.
  • Idempotency: Idempotency-Key header accepted on pickup-orders and reservations.
  • Alcohol guard: validation layer on POST /pickup-orders rejects any item where the joined product.is_alcohol = true. Tested explicitly in the integration suite.
  • Notifications: pickup-orders, event-reservations, inquiries POSTs emit a server-side WhatsApp message (via 360dialog or Twilio Business API) to the owner number, plus an email digest at end of day to avoid notification fatigue.

17. Recommended Visual Design (Highly Specific & Actionable)

17.1 Style Direction

CRUDO's visual language is dark editorial gastronomy — the world of a candle-lit cellar at 9pm, not a bright deli at noon. It draws from the Piscolabis family (dark, moody, artisan) and differentiates with:

  • A deeper, greener base palette (not Piscolabis' charcoal-brown-leaning tones) — this is wine cellar, not jamonería.
  • Cormorant Garamond as headline serif (more aged and gastronomic than Playfair Display, which is now over-used in restaurants).
  • Terracotta + aged gold accents for CTAs (warmer than ochre, less "gold leaf" than Piscolabis).
  • Letter-spaced uppercase microcopy for section labels — editorial magazine feel.
  • Photography contrast turned slightly down — low-key, warm, never saturated.

21. User Stories with Acceptance Criteria

US-01 — Browse seasonal cheese on mobile

As a foodie visiting from Instagram, I want to see what cheese is in season this week so I can decide quickly if I want to pick something up. - AC1: Home shows a "Esta temporada" section with at least 4 products marked is_seasonal=true. - AC2: Section visible above the fold within first scroll on iPhone 13. - AC3: Each card links to PDP and tracks select_item GA4 event. - AC4: Lazy-loaded images, no CLS.

US-02 — Reserve a tabla for pickup (non-alcohol)

As a customer, I want to assemble a cheese tabla and reserve it for pickup so I can grab it on my way home tonight. - AC1: I can add at least 2 non-alcohol products to "Mi tabla" from PDP or catalog card. - AC2: Wine PDPs show no "Añadir a mi tabla" button — only the "Pregúntanos por WhatsApp" CTA. - AC3: Drawer shows running total VAT-inclusive. - AC4: I can pick a date (only opening days) and a 30-min slot. - AC5: On submit, I receive a confirmation page with order ID + expectation that CRUDO will confirm by WhatsApp within 24h. - AC6: Owner receives a WhatsApp ping + end-of-day email digest with full order. - AC7: GA4 + Pixel purchase-equivalent custom event fires (pickup_request) with cart contents and total. - AC8: Form fails gracefully on validation, never on network — retries once. - AC9: API POST /pickup-orders rejects with HTTP 422 if any line item references is_alcohol=true (defensive — UI already prevents this).

US-02b — Inquire about a wine via WhatsApp

As a wine-curious customer, I want a fast way to ask if a specific bottle is available and reserve it for pickup. - AC1: Each wine PDP has a primary CTA "Pregúntanos por WhatsApp". - AC2: Tapping it opens wa.me/+34...?text=... with a prefilled message including product name and slug. - AC3: A discreet info line confirms: "Los vinos se reservan y se pagan en CRUDO." - AC4: GA4 outbound event wine_whatsapp_click fires with product slug. - AC5: On iOS Safari and Instagram in-app browser, the link opens WhatsApp without intermediate page.

US-03 — Reserve a tasting

As a customer, I want to reserve a seat at the natural wine tasting so I can attend. - AC1: Event detail page shows date, capacity, remaining seats (or "quedan pocas plazas" if < 30%). - AC2: Reservation form: name, email, phone, party size (1–4). - AC3: On submit, confirmation email sent + admin sees reservation. - AC4: If event is full, form is replaced by waitlist input.

US-04 — Subscribe to newsletter

As a visitor, I want to subscribe to the newsletter so I get notified about new arrivals and tastings. - AC1: Email field visible in footer + post-pickup confirmation. - AC2: Double opt-in via Brevo. - AC3: Consent timestamp + IP stored for RGPD compliance. - AC4: GA4 generate_lead event.

US-05 — Owner adds a new wine

As the CRUDO owner, I want to add a new wine to the catalog without calling a developer. - AC1: Login at /admin with email + password (JWT). - AC2: "Nuevo producto" form: name, type, producer, region, price, descriptions, seasonal/featured flags, primary image upload. - AC3: Save → product available on the public site within 60 seconds. - AC4: Validation prevents missing required fields. - AC5: Audit field updated_by recorded.

US-06 — Owner publishes an event

As the CRUDO owner, I want to publish a new tasting event with a hero image and reservation cap. - AC1: Event editor with date/time picker, capacity, price, description (markdown), image upload. - AC2: "Publicar" toggle controls visibility on public site. - AC3: Once published, event appears in /eventos sorted by date.

US-07 — Cookie consent compliant with AEPD

As any visitor, I want a clear cookie banner so my consent is properly captured. - AC1: First visit: banner with Aceptar / Rechazar / Configurar — equal visual weight. - AC2: No non-essential cookies set before consent. - AC3: GA4 + Pixel only fire after analytics/marketing consent. - AC4: Consent log stored 24 months. - AC5: Cookie policy page lists all cookies with provider, purpose, duration.

Appendix C — Domain Name Analysis & Recommendation

You are evaluating crudo.world and other ideas. Here is a structured analysis with a clear recommendation.

Evaluation criteria (in order of weight for CRUDO)

  1. Local discoverability in Madrid / Spain — does Google treat it as Spanish-relevant?
  2. Brand fit — does it feel premium, gastronomic, artisan?
  3. Memorability for word-of-mouth — can a customer tell a friend the URL after a glass of wine?
  4. Cost & availability
  5. Future-proofing for second location — does the TLD constrain you geographically?
  6. Email & operational — does it support pro email (hola@…) cleanly?

Options analyzed

Option Pros Cons Verdict
crudo.es Strongest local SEO signal in Spain, instantly recognizable as Spanish business, cheap (~€8/yr), simple to type, great for Spain-first strategy Likely already taken (verify); restricts to Spain narrative if you ever expand to Latin America/Italy Best if available — first to check
crudo.world Available, suggests aspiration & global curation (fits "we bring world wines/cheeses to Madrid"), distinctive Newer TLD, slightly less trusted by older audiences, less obvious .es-equivalent local SEO weight (mitigated by hreflang + GMB) Strong second choice — works narratively

Recommendation

Pursue this order, take the first that's available:

  1. crudo.es — register immediately if free. This is the single best signal for local SEO + brand simplicity. Combine with crudo.com if affordable as a redirect.
  2. crudo.world — your current candidate. It works narratively ("we bring the world's natural wines and artisan cheeses to a corner of Madrid"). Pair it with strong local SEO signals (hreflang es-ES, Google Business Profile, schema.org Restaurant.address.addressCountry=ES, Madrid-targeted content).
  3. crudomadrid.es — fallback if both above are unavailable or unreasonable.

Operational must-haves regardless of choice

  • Register the matching .com and .es even if you don't use them (defensive registrations, ~€20/yr total).
  • Email: set up hola@<domain> and pedidos@<domain> via Google Workspace (€6/user/mo) or Zoho Mail (free tier).
  • DNS via Plesk or the registrar by default; add a CDN provider later only if traffic/performance justifies it.
  • .es requires a Spanish CIF/NIE for registration — your existing legal entity covers this.
  • 301 redirect any non-canonical domains to the canonical one for SEO consolidation.

If you go with crudo.world (your current lean)

To compensate for the non-Spanish TLD on local SEO: - Set Google Search Console International Targeting → Country = Spain. - Use <html lang="es"> and <link rel="alternate" hreflang="es-ES" href="...">. - Strong, consistent NAP (Name-Address-Phone) across web + Google Business Profile + Instagram bio. - Aggressive local link-building: Madrid food blogs, Time Out Madrid, Spanish wine press. - Schema.org Restaurant with full address — this is what Google's local pack uses, not the TLD.

With these in place, crudo.world will not meaningfully underperform a .es domain in the local pack.
